Section 01

Big picture — start here

This project is a local travel assistant. You type a natural-language question about weather, driving time, towns on a route, restaurants, or putting a trip on your calendar. An orchestrator agent decides which specialist agents to ask; specialists call free public APIs (or write calendar files) for real data.

Fresher analogy: Think of a hotel concierge desk. You ask one person (the orchestrator). They don’t know every detail themselves — they call the weather desk, the maps desk, the restaurants desk, and the calendar desk, then summarize everything back to you.

You

Guest at the desk

CLI (run_agents.py) or Streamlit GUI (streamlit_app.py)

Orchestrator

Concierge

Reads your request, picks specialists, combines their answers into one reply.

Specialists

Weather / Travel / Dining / Calendar

Tools hit wttr.in, OSRM, Nominatim, Overpass — or write .ics files for Google Calendar.

LLM (Ollama)

The brain

Decides what to call and how to phrase the answer — not inventing map or venue data.

What you can ask

  • “Weather in Tokyo”
  • “Drive Paris to Lyon at 9:30 AM — towns and weather at arrival”
  • “Restaurants in intermediate towns between Boston and Portland”
  • “Add Mumbai→Hyderabad tomorrow 10 AM to my calendar” (duration from OSRM, not guessed)
  • Combined: travel + weather + dining + “add that trip to my calendar” (orchestrator)

Section 02

Everything runs on your machine. The “AI brain” is a local model via Ollama. Agents are built with LangChain’s high-level create_agent (ReAct-style), with conversation state from LangGraph’s MemorySaver.

Section 04

How the LLM is the brain

The LLM does not store live weather or restaurant databases. Its job is judgment: understand the user, choose tools, interpret tool results, write a clear answer.

Brain

LLM (Qwen via Ollama)

Language understanding, planning which tool to call, summarizing results.

Hands

@tool functions

Python code that hits APIs. Deterministic. Returns text observations.

Rules

system_prompt

“Never invent weather / venues / calendar paths — always use tools.” Guides behavior.

Short memory

MemorySaver

Remembers earlier turns in this session (same thread_id).

How every agent is built (same pattern)

Weather, travel, restaurant, calendar, and orchestrator all use make_chat_ollama(...):

llm = make_chat_ollama(
    model=model,              # default qwen3.5:latest
    temperature=temperature,  # default 0.2
    top_k=top_k,              # default 10 (GUI / optional)
)
# returns a LangGraph runnable
return create_agent(
    llm,
    tools=[...],
    system_prompt="...",
    checkpointer=MemorySaver(),
)
Shared factory: agent_common.make_chat_ollama keeps CLI defaults while Streamlit passes sidebar selections into every build_agent(model=..., temperature=..., top_k=...) — including nested specialists under the orchestrator.

Temperature & top-k

Defaults: temperature 0.2, top-k 10 — good for deterministic tool choice. Streamlit sidebar lets you raise temperature for freer wording or change top-k / model without editing code.

Section 05

One agent turn — the ReAct loop

ReAct = Reason + Act. The model thinks, may call a tool, reads the result (observation), then thinks again — until it can answer in plain text.

  1. You send a question

    invoke_agent wraps it as a HumanMessage and calls graph.invoke(...) with a thread_id.

  2. LLM reasons

    Sees system prompt + conversation. Decides: answer now, or emit one/more tool_calls.

  3. Framework acts

    LangGraph runs the matching Python @tool (HTTP call or nested specialist agent).

  4. Observation returns

    Tool output is appended as a message. LLM sees real data (weather lines, ETAs, venue lists, .ics paths).

  5. Final answer

    LLM writes an AIMessage (with Ollama usage_metadata). extract_assistant_reply returns the text; finish_usage_span attaches tokens and trip state to the LangSmith run.

The tiny “glue” file: agent_common.py

# One turn — named LangSmith span + tokens + trip
tid = thread_id or uuid.uuid4().hex
config = {
    "configurable": {"thread_id": tid},
    "run_name": agent_name,   # orchestrator | weather | travel | …
    "tags": [agent_name, "cli" or "gui"],
}
with agent_trace(agent_name, …) as run:
    result = graph.invoke({"messages": [HumanMessage(content=q)]}, config)
    usage = usage_from_messages(result["messages"])
    finish_usage_span(usage, agent_name=agent_name, run=run, trip=snapshot_for_trace())
return extract_assistant_reply(result["messages"])

Interactive mode (run_interactive) keeps one session_tid so follow-ups like “what about tomorrow?” still know the place. Type /reset to start a new thread.

Section 06

How agents communicate

There is no message bus, no shared queue, no AutoGen group chat. Communication is agents-as-tools plus typed trip state (trip_state.py): the orchestrator LLM calls a specialist, and structured fields (origin, destination, start_time, duration_s) are stored for the session so calendar/restaurants do not re-guess drive time from English.

Pattern name: Supervisor / router with nested agents

Orchestrator builds four specialist graphs once in build_agent(), then exposes them as @tools. When the orchestrator model chooses ask_travel_specialist or ask_calendar_specialist, Python runs that specialist’s ReAct graph and returns the final text.

Real code shape (orchestrator_agent.py)

weather_graph = build_weather_agent(**llm_kwargs)
travel_graph = build_travel_agent(**llm_kwargs)
restaurant_graph = build_restaurant_agent(**llm_kwargs)
calendar_graph = build_calendar_agent(**llm_kwargs)

@tool
def ask_travel_specialist(query, origin="", destination="", mode="driving", start_time="") -> str:
    update_trip(origin=origin, destination=destination, mode=mode, start_time=start_time)
    return run_travel_query(travel_graph, compose_specialist_query(query, specialist="travel"))

@tool
def ask_calendar_specialist(query, origin="", destination="", start_time="", mode="") -> str:
    update_trip(origin=origin, destination=destination, start_time=start_time, mode=mode)
    return run_calendar_query(calendar_graph, compose_specialist_query(query, specialist="calendar"))

create_agent(make_chat_ollama(**llm_kwargs), tools=[
    ask_weather_specialist,
    ask_travel_specialist,
    ask_restaurant_specialist,
    ask_calendar_specialist,
], ...)

What the docstring does

Tool docstrings become the schema description the LLM sees. They tell the orchestrator when to delegate (weather vs route vs dining vs calendar) and to pass a clear, self-contained sub-question.

Memory boundary: Specialist run_query calls omit thread_id, so each delegation gets a fresh ephemeral thread. Session memory lives on the orchestrator conversation, not inside nested specialist hops. Typed trip state is the exception: it is keyed by the orchestrator thread_id so a later ask_calendar_specialist can read duration_s that travel just wrote. The same snapshot is written onto LangSmith span outputs as trip.
Guardrails AI: guardrails_common.py runs local validators (Apache-2.0, no Hub models) on the user turn and on each specialist hop. Abusive language is refused. Prompt injection is caught and answered with a fixed reply that does not follow the override (how to re-ask a normal weather/travel/dining/calendar question). A dining question sent to the weather specialist (or similar misrouting) is refused with a guardrail LangSmith tag. Disable with AGENTIC_AI_GUARDRAILS=false.

You can also skip the orchestrator

run_agents.py --client weather|travel|restaurants|calendar runs a specialist directly — same brain + tools, no supervisor layer.

Section 09

Travel calendar agent

calendar_agent.py turns “add this trip to my calendar” into an accurate event: start day+time from the user, end time from live OSRM routing (not a guessed 4h/6h), then writes .ics, builds a Google TEMPLATE link, and opens the browser so you click Save.

Bug that was fixed: Orchestrator sometimes invented “10 AM–4 PM (6 hours)” while travel reported ~8h 47m, and defaulted start to today 08:00 instead of tomorrow 10:00. Road-trip calendars now require an explicit day in start_time and take duration from OSRM.

Required

start_time with day

e.g. tomorrow 10:00 AM or 2026-07-30 10:00. Empty / “10 AM” alone is rejected.

Authoritative

OSRM duration

create_travel_calendar looks up the route; e.g. Mumbai→Hyderabad ≈ 8h 47m → 10:00–18:47.

CLI / GUI

Open Google Calendar

CLI: open <url>. GUI (AGENTIC_AI_GUI=1): skip auto-open; user clicks Add to Calendar.

Optional

Calendar API

If credentials.json exists, also inserts into primary calendar.

Example flow (plan trip + calendar)

You
plan trip from mumbai to hyderabad by road tomorrow 10 AM and add it to calendar
Orchestrator
Calls travel specialist, then calendar with origin/destination and tomorrow 10:00 AM — does not invent duration.

create_travel_calendar(..., start_time="tomorrow 10 AM", duration="") → _osrm_duration_seconds → ~527 min
Result
Local window e.g. tomorrow 10:00 → 18:47 · .ics + latest_invite.json · CLI opens browser or GUI shows Add to Calendar

Key helpers in code

_parse_event_start("tomorrow 10 AM")   # today/tomorrow / YYYY-MM-DD

Section 11

LangSmith — debug the flow

tracing_common.py turns every user turn into a named LangSmith trace: orchestrator → specialist → tool → HTTP API, with Ollama token counts and typed trip state (origin, duration_s, start_time) on each agent span.

Enable: copy .env.example to .env and set LANGSMITH_API_KEY. Tracing turns on automatically (project agentic-ai). Set LANGSMITH_TRACING=false to disable without removing the key. Open traces at smith.langchain.com.

Parent span

Named agent turn

invoke_agent(..., agent_name="orchestrator") → run name orchestrator / weather / travel / restaurants / calendar.

Nested

Specialists + tools

Orchestrator tools call specialist run_query, which starts a child span. LangChain also traces each @tool.

HTTP

@traceable helpers

Nominatim, OSRM, wttr.in, Overpass, calendar OSRM / .ics / Google URL — visible as retriever/tool spans.

Tokens

usage_metadata

From ChatOllama prompt_eval_count / eval_count. Orchestrator rollup includes nested specialists (by_agent).

Trip

typed trip state

trip_state.snapshot_for_trace() on span inputs (before) and outputs/metadata (after). HTTP @traceable helpers get the same trip object. Tag: trip.

What one orchestrator query looks like in LangSmith

1 · Root
orchestrator chain — question in, reply + token_summary + trip out. Tags: orchestrator, cli or gui, and trip when a route is in state.
2 · LLM
ChatOllama ReAct steps (tool-call then final answer). Each AIMessage carries usage_metadata.
3 · Tool
ask_travel_specialist (and maybe calendar / weather / restaurants) — nested agent graphs.
4 · Child agent
Span named travel (or other specialist). Own LLM calls + tools.
5 · HTTP
nominatim.geocode · osrm.fetch_route · wttr.current / wttr.forecast_at_time · overpass.post · calendar.*
6 · Tokens
Root span: input_tokens + output_tokens + total_tokens + llm_calls, plus by_agent breakdown. CLI prints the same line; GUI shows it as a caption under the reply.
7 · Trip
Outputs/metadata trip: origin, destination, start_time, duration_s, duration_human, trip_id. Travel writes duration; calendar/restaurants read the same object. HTTP spans copy it via drop_http_client.

Key helpers

configure_langsmith()          # load .env; enable if API key present
agent_trace("orchestrator", …)  # parent span for one user turn
usage_from_messages(messages)   # sum Ollama usage_metadata / eval_count
finish_usage_span(…)            # attach usage_metadata + trip; roll up to parent
snapshot_for_trace()            # origin / duration_s / start_time for LangSmith
@traceable(name="osrm.fetch_route")  # HTTP helpers; process_inputs adds trip
Token source: Ollama reports prompt_eval_count (input) and eval_count (output) on each generation. ChatOllama copies that onto AIMessage.usage_metadata. Nested specialist turns are summed into the orchestrator span so you can see the full cost of “plan trip + add to calendar”.
Trip on traces: finish_usage_span writes trip onto the run’s outputs and metadata after tools (that is when duration_s exists). Inputs show trip only if the session already had a route. HTTP @traceable helpers attach the same snapshot so an osrm.fetch_route span is filterable by origin.
