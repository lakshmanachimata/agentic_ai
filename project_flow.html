Section 01

Big picture — start here

This project is a local travel assistant. You type a natural-language question about weather, driving time, towns on a route, restaurants, or putting a trip on your calendar. An orchestrator agent decides which specialist agents to ask; specialists call free public APIs (or write calendar files) for real data.

Fresher analogy: Think of a hotel concierge desk. You ask one person (the orchestrator). They don’t know every detail themselves — they call the weather desk, the maps desk, the restaurants desk, and the calendar desk, then summarize everything back to you.

You

Guest at the desk

Type questions in the CLI: python run_agents.py

Orchestrator

Concierge

Reads your request, picks specialists, combines their answers into one reply.

Specialists

Weather / Travel / Dining / Calendar

Tools hit wttr.in, OSRM, Nominatim, Overpass — or write .ics files for Google Calendar.

LLM (Ollama)

The brain

Decides what to call and how to phrase the answer — not inventing map or venue data.

What you can ask

  • “Weather in Tokyo”
  • “Drive Paris to Lyon at 9:30 AM — towns and weather at arrival”
  • “Restaurants in intermediate towns between Boston and Portland”
  • “Create a calendar event for driving Paris to Lyon tomorrow 9 AM lasting 4 hours”
  • Combined: travel + weather + dining + “add that trip to my calendar” (orchestrator)

Section 02

Tech stack & frameworks

Everything runs on your machine. The “AI brain” is a local model via Ollama. Agents are built with LangChain’s high-level create_agent (ReAct-style), with conversation state from LangGraph’s MemorySaver.

Section 04

How the LLM is the brain

The LLM does not store live weather or restaurant databases. Its job is judgment: understand the user, choose tools, interpret tool results, write a clear answer.

Brain

LLM (Qwen via Ollama)

Language understanding, planning which tool to call, summarizing results.

Hands

@tool functions

Python code that hits APIs. Deterministic. Returns text observations.

Rules

system_prompt

“Never invent weather / venues / calendar paths — always use tools.” Guides behavior.

Short memory

MemorySaver

Remembers earlier turns in this session (same thread_id).

How every agent is built (same pattern)

Weather, travel, restaurant, calendar, and orchestrator all follow:

llm = ChatOllama(
    model="qwen2.5:7b",
    base_url="http://127.0.0.1:11434",
    temperature=0.2,
)
# returns a LangGraph runnable
return create_agent(
    llm,
    tools=[...],          # @tool functions the model may call
    system_prompt="...",  # role + guardrails
    checkpointer=MemorySaver(),
)
Key idea: create_agent wires a ReAct-style loop for you. You do not hand-write a custom StateGraph in this project — LangChain’s helper builds that graph under the hood.

Temperature = 0.2

Low temperature → more deterministic tool choice and wording. Good for routing/agent systems where weird creative guesses would be bad.

Section 05

One agent turn — the ReAct loop

ReAct = Reason + Act. The model thinks, may call a tool, reads the result (observation), then thinks again — until it can answer in plain text.

  1. You send a question

    invoke_agent wraps it as a HumanMessage and calls graph.invoke(...) with a thread_id.

  2. LLM reasons

    Sees system prompt + conversation. Decides: answer now, or emit one/more tool_calls.

  3. Framework acts

    LangGraph runs the matching Python @tool (HTTP call or nested specialist agent).

  4. Observation returns

    Tool output is appended as a message. LLM sees real data (weather lines, ETAs, venue lists, .ics paths).

  5. Final answer

    LLM writes an AIMessage. extract_assistant_reply returns that last text to the CLI.

The tiny “glue” file: agent_common.py

# One turn
tid = thread_id or uuid.uuid4().hex
config = {"configurable": {"thread_id": tid}}
result = graph.invoke({"messages": [HumanMessage(content=q)]}, config)
return extract_assistant_reply(result["messages"])

Interactive mode (run_interactive) keeps one session_tid so follow-ups like “what about tomorrow?” still know the place. Type /reset to start a new thread.

Section 06

How agents communicate

There is no message bus, no shared queue, no AutoGen group chat. Communication is agents-as-tools: the orchestrator LLM calls a tool whose body runs another agent to completion and returns a string.

Pattern name: Supervisor / router with nested agents

Orchestrator builds four specialist graphs once in build_agent(), then exposes them as @tools. When the orchestrator model chooses ask_travel_specialist or ask_calendar_specialist, Python runs that specialist’s ReAct graph and returns the final text.

Real code shape (orchestrator_agent.py)

weather_graph = build_weather_agent()
travel_graph = build_travel_agent()
restaurant_graph = build_restaurant_agent()
calendar_graph = build_calendar_agent()

@tool
def ask_calendar_specialist(query: str) -> str:
    """Delegate to the travel-calendar specialist…"""
    return run_calendar_query(calendar_graph, query.strip())

# same idea for weather + travel + restaurants…

create_agent(llm, tools=[
    ask_weather_specialist,
    ask_travel_specialist,
    ask_restaurant_specialist,
    ask_calendar_specialist,
], ...)

What the docstring does

Tool docstrings become the schema description the LLM sees. They tell the orchestrator when to delegate (weather vs route vs dining vs calendar) and to pass a clear, self-contained sub-question.

Memory boundary: Specialist run_query calls omit thread_id, so each delegation gets a fresh ephemeral thread. Session memory lives on the orchestrator conversation, not inside nested specialist hops.

You can also skip the orchestrator

run_agents.py --client weather|travel|restaurants|calendar runs a specialist directly — same brain + tools, no supervisor layer.

Full walkthrough — one mixed question

Example: “Drive Milan to Rome at 8 AM; towns with weather; restaurants in those towns.”

1 · You
Run python run_agents.py, type the trip question at >.
2 · Launcher
build_orchestrator() builds orch + four specialist graphs. run_interactive keeps a session thread_id.
3 · Orchestrator LLM
Reads system prompt: never invent data; rewrite into focused sub-questions; may call several tools in one turn.
4 · Tool call
ask_travel_specialist("Drive Milan to Rome leaving 8 AM, major towns + weather…")
5 · Travel agent
Its own ReAct loop chooses get_route_stops_with_weather → route_common: geocode → OSRM polyline → sample towns → wttr timed forecast.
6 · Tool call
ask_restaurant_specialist("Restaurants in intermediate towns Milan→Rome…")
7 · Restaurant agent
Often find_restaurants_at_towns_on_route → discover towns → Overpass amenity search per town.
8 · (optional) Calendar
If you also ask “add this trip to my calendar” → ask_calendar_specialist writes an .ics, builds a Google add link, and opens it in the browser for you to Save.
9 · Orchestrator
Gets observations, writes one combined natural-language answer, printed to stdout.

Section 09

Travel calendar agent

calendar_agent.py turns “add this trip to my calendar” into an .ics file, a Google Calendar TEMPLATE link, and opens that link in your browser so you can click Save manually — no OAuth required for this path.

Always

.ics file

Written under calendar_events/. Import via Google Calendar → Settings → Import.

Always

Quick-add link

Prefills Google Calendar’s create form (action=TEMPLATE).

Always (new)

Auto-open browser

On macOS runs open <url>; elsewhere uses webbrowser.open. You click Save.

Optional

Calendar API

If credentials.json + Google packages exist, also inserts into your primary calendar.

Example flow

You
python run_agents.py -c calendar "Drive Paris to Lyon tomorrow 9 AM for 4 hours — add to calendar"
Calendar LLM
Calls create_travel_calendar(origin="Paris", destination="Lyon", start_time="tomorrow 9 AM", duration="4 hours")
Tool
Builds iCalendar VEVENT → saves calendar_events/….ics → builds Google TEMPLATE URL → _open_calendar_url → open <url> on macOS
Browser
Google Calendar “Add event” page opens prefilled — you click Save
CLI reply
Reports .ics path, link, and “Browser: opened Google Calendar add-event page…”
Code: _open_calendar_url() in calendar_agent.py — subprocess.run(["open", url]) on Darwin; webbrowser.open elsewhere. Called from _create_event_bundle right after the TEMPLATE URL is built.
Orchestrator tip: After travel results, say “add that trip to my calendar” — the orchestrator delegates to ask_calendar_specialist; the browser tab still opens the same way.
